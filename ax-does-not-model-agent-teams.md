# AX does not declaratively model an agent team

**Takeaway:** AX currently declares isolated task sandboxes, not teams. Its YAML has no built-in roles, dependency DAG, result handoff, or team topology; those relationships must be implemented by software outside AX or by the program running inside a task.

At [`e09ed1b`](https://github.com/google/ax/tree/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7), `ax apply` accepts exactly three public resource kinds—`Task`, `Workspace`, and `Model`—and rejects other kinds ([manifest dispatch](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/cmd/ax/main.go#L248-L303)). Their schemas have different jobs:

- A **`Task`** describes one execution unit: suspend state, image, command, environment, resource requests, workspace bindings, and debug access ([`TaskSpec`](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/pkg/apis/v1alpha1/ax.proto#L60-L112)).
- A **`Workspace`** describes reusable environment inputs—Git repositories, MCP configuration, and skills—not a worker or teammate ([`WorkspaceSpec`](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/pkg/apis/v1alpha1/ax.proto#L144-L195)). A task binding's `goal` is a first-boot setup request: the runner prepares that task's workspace and attempts to pass the goal to its bootstrap agent before starting the task command; it is not an ongoing agent objective or delegated role ([setup path](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/workspace/setup.go#L76-L127), [bootstrap behavior](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/workspace/setup.go#L272-L314)). The resource is reusable, but its files are not a shared team volume: the runner materializes it inside each task sandbox, and each task actor gets its own durable `/workspace` volume ([workspace concept](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md#L22-L32), [actor volume](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/substrate/client.go#L238-L262)).
- A **`Model`** is provider/model/parameters/secret configuration; `TaskSpec` has no model reference ([`ModelSpec`](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/pkg/apis/v1alpha1/ax.proto#L197-L222)).

These are complete typed manifest schemas, not open-ended YAML: decoding rejects unknown fields ([YAML decoder](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/pkg/apis/v1alpha1/types.go#L43-L59)). Therefore, at this revision, adding `role`, `dependsOn`, `handoff`, or `team` keys does not create team semantics.

`spec.command` also remains a single-task boundary. The controller serializes the task and its bound workspaces into the actor environment ([controller](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/controller/reconciler.go#L126-L169)); the container starts `ax-task-runner`, which launches `spec.command` as a supervised child in the first workspace ([runner launch](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/runner/runner.go#L106-L187)). Readiness means workspace setup finished: the runner marks ready *before* launching the child, and it stays up after that child exits ([runner lifecycle](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/runner/runner.go#L155-L199)); the control plane does not receive the child's exit status ([runner contract](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L30-L45)). `Ready` is therefore not “all agents completed” or even “the task command completed.”

To run a team, either use an external coordinator to create/watch separate `Task`s and explicitly handle dependencies and result transfer, or make `spec.command` your own in-container multi-agent harness. AX deliberately leaves planning, delegation, retries, and fan-out to the agent rather than modeling that shape ([task concept](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md#L5-L20)). Roadmap items such as stateful task branching and configurable in-sandbox harnesses are future direction, not a current team manifest ([roadmap](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/roadmap.md#L15-L31)).
