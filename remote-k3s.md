# An existing remote k3s cluster can host AX, but not by itself

**Question:** Can my remote k3s replace a local kind cluster? **Answer:** Potentially yes. AX needs Kubernetes with [Agent Substrate already running](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/README.md#L59-L91), not Kubernetes on the Mac. With a reachable kubeconfig, the Mac's `ax` CLI can use the remote context and [port-forward to the AX service](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/tunnel/tunnel.go#L177-L240). Local Docker and kind are unnecessary merely to use that cluster.

The existing k3s installation is **not enough on its own**. The AX-pinned Substrate revision requires recent certificate APIs, gVisor-capable Linux workers with a WorkerPool, actor snapshot storage, and images pullable by the remote nodes. Its documented installers target kind or GKE, so a remote non-GCP cluster needs reviewed adaptations before installation. [Pinned Substrate revision](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/go.mod#L3-L9) · [Substrate kind API configuration](https://github.com/agent-substrate/substrate/blob/672533541dbf/hack/create-kind-cluster.sh#L103-L113) · [AX snapshot default](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/deploy/ax-controller.yaml#L79-L84).

[The remote-k3s preflight guide](remote-k3s-preflight.md) explains the six checks and restart risks. [Kubernetes is needed for real Tasks](kubernetes-required-for-tasks.md) distinguishes this from a local runner experiment. No remote cluster was inspected or changed for this research.
