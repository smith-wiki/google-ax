# An agent brain calls AX as a task control plane

**Question:** Must the agent brain be separate, and how does it ask AX to run work? **Answer:** The agent logic (model, prompts, tool choices, delegation) must come from *your* program; AX does not supply it. That program may run outside AX as a trusted coordinator, or inside a `Task` as its `spec.command`. AX's `Task` is the execution sandbox primitive, not a built-in planner ([AX concepts](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md#L5-L9), [runner](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L9-L26)).

```text
user → your agent/coordinator → trusted AX client → AX control plane
                                                    → Agent Substrate actor → child command
            ← result via a handoff that your application defines ←
```

The brain chooses and submits the child `Task`; AX asks Substrate to run its image and `spec.command`. The brain does not execute that child program itself ([AX architecture](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/DESIGN.md#L3-L44)).

The **programmatic interface** is the typed `ax.v1alpha1.AX` **gRPC** service: `UpdateTask` creates or updates a `Task`; `GetTask`, `ListTasks`, and `WatchTask` inspect it; `SuspendTask`, `ResumeTask`, and `DeleteTask` control its lifecycle. The `ax` CLI is a client of that same service: `ax apply -f task.yaml` parses YAML locally and calls `UpdateTask`, not a Kubernetes Job/CRD API or an HTTP endpoint that receives YAML ([proto](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/pkg/apis/v1alpha1/ax.proto#L24-L49), [apply](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/cmd/ax/main.go#L207-L271)). From a trusted machine the CLI can use a Kubernetes context to port-forward the AX Service; a custom trusted application can use the gRPC client directly ([tunnel](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/tunnel/tunnel.go#L177-L240)).

**This is a control interface, not a completion/result protocol.** `WatchTask` reports sandbox lifecycle/readiness; the default runner logs its child command's exit code but does not report that exit to the AX control plane. Your coordinator must define how a child reports *success, failure, and artifacts* (for example through its own store or a restricted callback) before it can make a dependency decision ([runner contract](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L30-L43), [why AX is not a team graph](ax-does-not-model-agent-teams.md)). The in-task `AX_METADATA_URL` is a local **read-only** endpoint for that task's configuration, not an API for creating child tasks ([sandbox metadata](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/sandbox.md#L12-L26)).

**Trust boundary:** Do not give an arbitrary sandbox the cluster kubeconfig or unrestricted AX API access just to allow delegation. In this AX revision, the server constructs a bare gRPC server with no authentication interceptor and serves unencrypted HTTP/2; the CLI also creates an insecure gRPC client. Network reachability to this endpoint is therefore a privilege, not an agent tool to expose by default ([server registration](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/server/server.go#L38-L66), [server transport](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/cmd/ax-server/main.go#L65-L84), [client transport](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/cmd/ax/main.go#L197-L205)). A narrow authenticated tool/service operated by a trusted coordinator would be an **application design choice**, not a built-in AX feature.

**What is the coordinator physically?** It is an ordinary long-lived process you operate: for example a backend service running an agent framework plus its own conversation/artifact store, or a trusted script operated by a human. It decides whether to split a job, issues `ax apply` or `UpdateTask`, receives each worker's result through an application-defined channel, and assembles the answer. It can itself run in an AX Task, but then it still needs a deliberately secured route to the AX API. Neither AX nor Agent Substrate creates this program, its session store, or its result protocol ([sessions across Tasks](sessions-live-above-tasks.md), [AX Task boundary](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md#L5-L9)).

**What does `ax apply` buy this coordinator?** It creates or updates execution resources with per-task isolation, workspace preparation, and suspend/resume through Substrate. If `spec.command` is an agent executable, those resources are effectively its *subagent sandboxes*; if it is an ordinary script, they are ordinary sandboxed jobs. `ax apply` does **not** decompose the request, share the session, detect that the agent finished, or synthesize the combined answer ([API operations](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/pkg/apis/v1alpha1/ax.proto#L24-L49), [runner completion boundary](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L41-L43)). If decomposition and synthesis are the hard part, AX alone is not the application solution.

**Practical starting point:** keep the brain/coordinator in a trusted process outside AX, give it a narrowly scoped way to request tasks and receive their results, and place disposable workers in AX only if sandbox/lifecycle operations justify the [AX plus Agent Substrate stack](ax-solves-agent-operations.md). An in-AX brain is possible, but packaging its agent executable, AX client, secure access path, and result handoff is your responsibility. No cluster or agent was run for this explanation.
