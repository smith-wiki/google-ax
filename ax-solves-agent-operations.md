# AX solves the operations of running agents, not their teamwork

**Core problem:** an agent is not just a function call. It may run untrusted tools against a mutable checkout, retain files across sessions, need a prepared environment, and spend a long time waiting or working. Running many such isolated workspaces, creating and inspecting them consistently, and pausing them without discarding their files becomes an infrastructure problem. AX is a declarative control plane for **each agent execution sandbox**, backed by [Agent Substrate](https://github.com/agent-substrate/substrate), not an engine that decides what a team of agents should do ([AX motivation](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/README.md#L45-L57), [Task concept](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md#L5-L9)).

- **`Task`** declares the isolated image and command, with a lifecycle one can inspect, suspend, resume, and delete. Substrate supplies the actors underneath; the agent program itself is the task's command ([concepts](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md#L5-L20), [runner contract](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L9-L26)).
- **`Workspace`** prepares Git repositories, MCP configuration, and skills *inside each sandbox*. Reusing the specification does not imply a shared filesystem between tasks ([concepts](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md#L22-L32)).
- **`Model`** names model/provider configuration used by AX components; it is not a team role and `TaskSpec` has no `modelRef` that automatically configures an arbitrary agent executable ([concepts](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md#L34-L38), [schema](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/pkg/apis/v1alpha1/ax.proto#L70-L112)).

AX's **scale rationale** is specific: storing millions of short-lived tasks as Kubernetes CRDs would pressure etcd and the Kubernetes control plane. Its API stores task state in Redis, uses Redis Streams for controller work, and asks Substrate to create and activate actors. “Billions of tasks” is the project's *design goal*, not a throughput measurement established by this research ([design](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/DESIGN.md#L3-L44), [project claim](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/README.md#L11-L13)).

**What AX does not solve:** deciding roles/prompts, scheduling task dependencies, transferring one agent's output to another, or reporting whether a task's agent command succeeded. A separate coordinator or agent harness must own those decisions ([team boundary](ax-does-not-model-agent-teams.md), [runner exit behavior](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L41-L43)). Current suspend/resume restores files into a fresh process, *not* a paused in-memory agent; automatic idle suspension, budgets, and governance are roadmap items ([runner state](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L21-L26), [roadmap](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/roadmap.md#L3-L40)).

**Decision rule:** if one or two agents already run reliably on a laptop or existing cluster, AX plus Substrate probably adds more operational machinery than it removes. If the hard problem is operating a large fleet of disposable but stateful sandboxed agents with repeatable setup and lifecycle control, AX targets that problem. This is a fit assessment from its architecture, not a production benchmark. See [why remote k3s is not sufficient by itself](remote-k3s.md) and [why a team is not one AX manifest](ax-does-not-model-agent-teams.md).
