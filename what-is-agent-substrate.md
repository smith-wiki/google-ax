# Agent Substrate separates logical actors from physical Kubernetes workers

**Agent Substrate is a Kubernetes-backed runtime for isolated, stateful workloads.** Its unit of work is a logical **Actor**—an instance of an `ActorTemplate`—while a **Worker** is a record for a warm physical worker Pod. Kubernetes provisions and scales those Pods; Substrate's own control plane schedules actors, manages their lifecycle and snapshots, and routes traffic to wherever an actor currently runs. It is deliberately a runtime, not an SDK for writing agents ([Substrate overview](https://github.com/agent-substrate/substrate/blob/22ba860e0f32e20713165b96abd81f6f96da620c/README.md#L5-L14), [current glossary](https://github.com/agent-substrate/substrate/blob/22ba860e0f32e20713165b96abd81f6f96da620c/docs/glossary.md#L43-L71)).

## Why not one ordinary Pod per agent?

Agent-like programs are bursty: they may wait much longer than they compute. One Pod per agent therefore leaves idle Pods consuming finite cluster capacity; keeping millions of rapidly changing agent records in the Kubernetes API and waiting for the normal Pod scheduling path would also work against the intended scale and wake-up latency. Substrate keeps the lower-frequency infrastructure lifecycle in Kubernetes, but moves high-frequency actor assignment and state transitions into a focused control plane. This is the project's architectural rationale—not an independently verified performance result—and that architecture document warns that parts remain aspirational ([rationale and warning](https://github.com/agent-substrate/substrate/blob/22ba860e0f32e20713165b96abd81f6f96da620c/docs/architecture.md#L1-L14), [Kubernetes limitations and division of responsibility](https://github.com/agent-substrate/substrate/blob/22ba860e0f32e20713165b96abd81f6f96da620c/docs/architecture.md#L149-L173)).

A concrete model: a pool might have **8 ready worker Pods and 100 actor records**. That does **not** mean either 100 Pods or a fixed concurrency of 8. A worker can host several active actors, each in its own sandbox, until its actor or compute limit is reached; actors not currently occupying capacity remain suspended and many more can be multiplexed through the pool over time ([Actor and Worker definitions](https://github.com/agent-substrate/substrate/blob/22ba860e0f32e20713165b96abd81f6f96da620c/docs/glossary.md#L43-L50)).

## Lifecycle and routing

1. **Create:** `CreateActor` records the actor as suspended and associates it with an immutable template and its initial golden-snapshot reference; creation need not allocate a dedicated Pod.
2. **Resume and route:** a request carrying `ate-target-actor: <atespace>/<actor>` reaches `atenet`. If the actor is suspended, the control plane selects available worker capacity; node supervisor `atelet` fetches the snapshot, and in-Pod `ateom` restores the gVisor or microVM sandbox. The router then tunnels the request to that worker.
3. **Suspend:** Substrate checkpoints the actor, stores the committed snapshot externally, and frees the worker capacity. A later request can restore it on a different worker.

The state machine and request path are documented together in the [actor lifecycle](https://github.com/agent-substrate/substrate/blob/22ba860e0f32e20713165b96abd81f6f96da620c/docs/architecture.md#L378-L424); the component boundary that decouples a worker Pod from its sandboxed process is described in the [node supervisor and sandbox classes](https://github.com/agent-substrate/substrate/blob/22ba860e0f32e20713165b96abd81f6f96da620c/docs/architecture.md#L320-L338).

**Snapshot semantics depend on configuration.** Current Substrate documentation defines `Full` snapshots as process memory, root-filesystem delta, and durable directories; `Data` snapshots retain only snapshot-capable durable directories and discard current process memory and other rootfs writes. Suspend uploads the configured committed scope to GCS or S3; resume either restores a valid full snapshot or combines/restores data according to the template's resume source ([snapshot scopes and resume sources](https://github.com/agent-substrate/substrate/blob/22ba860e0f32e20713165b96abd81f6f96da620c/docs/glossary.md#L109-L157)).

## Where AX fits—and an important version distinction

AX is the higher layer: it turns declarative `Task`, `Workspace`, and `Model` resources into agent execution sandboxes, while using Substrate actors for sandbox execution and lifecycle ([AX overview](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/README.md#L11-L13), [AX-to-Substrate reconciliation](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/controller/reconciler.go#L171-L218)). It does not change Substrate into an agent framework: Substrate does not decide prompts, roles, delegation, dependencies, or team workflow, and AX intentionally leaves the shape of an agent's task tree to the agent or another coordinator ([Substrate boundary](https://github.com/agent-substrate/substrate/blob/22ba860e0f32e20713165b96abd81f6f96da620c/README.md#L9-L13), [AX Task boundary](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md#L5-L9)).

Do not project current Substrate's full-memory capability onto this older AX integration. AX commit `e09ed1b` pins Substrate `672533541dbf` ([module pin](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/go.mod#L3-L8)) and configures both pause and commit as `Data` scope for a single durable directory mounted at `/workspace`, with resume from a golden snapshot plus that data ([template construction](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/substrate/client.go#L238-L270)). Its runner contract is explicit: `/workspace` files survive, but resume starts a fresh container and process tree—not the agent process paused in RAM ([runner contract](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L21-L26)).

Finally, current Substrate at `22ba860` is explicitly **pre-1.0**, makes no backward-compatibility guarantee, and targets only the latest stable Kubernetes release plus the previous minor ([status and compatibility](https://github.com/agent-substrate/substrate/blob/22ba860e0f32e20713165b96abd81f6f96da620c/README.md#L46-L54)); AX `e09ed1b` likewise warns of breaking changes before stability ([AX warning](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/README.md#L6-L13)). An existing remote k3s cluster is therefore not automatically a compatible Substrate installation—see [the remote-k3s caveat](remote-k3s.md). For the division between infrastructure and multi-agent coordination, see [AX solves agent operations, not their teamwork](ax-solves-agent-operations.md).
