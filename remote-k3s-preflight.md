# Six checks before AX can run on remote k3s

This is a compatibility checklist for an existing cluster, not a deployment recipe. Start with [the short answer](remote-k3s.md): remote k3s may replace local kind, but it does not supply Agent Substrate, worker capacity, snapshot storage, or an image registry.

This guide complements [Trying AX on an Apple Silicon Mac](getting-started-on-mac.md). Source baseline: [`google/ax` `e09ed1b`](https://github.com/google/ax/tree/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7), whose module pins Agent Substrate [`672533541dbf`](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/go.mod#L3-L9). It does not assume that the existing cluster meets these requirements, and nothing below was run against it.

## What moves off the Mac?

| Place | Responsibility |
|---|---|
| **Mac client** | Keep a protected kubeconfig, `kubectl`, and the pinned `ax` CLI. AX selects an explicit `--context`, `KUBECONTEXT`, or the kubeconfig current context, then starts/reuses a local `kubectl port-forward` to `svc/ax-server`; it does not need AX exposed publicly ([context resolution](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/tunnel/context.go#L30-L69), [tunnel](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/tunnel/tunnel.go#L177-L240)). **Docker and kind are not required on the Mac merely to use this remote cluster.** Some image-building tool is needed only if the Mac will build and publish images. |
| **k3s server node(s)** | Serve a compatible Kubernetes API and the beta certificate resources Substrate consumes. k3s exposes Kubernetes component flags through `--kube-apiserver-arg`, `--kube-controller-manager-arg`, and `--kubelet-arg` ([server options](https://docs.k3s.io/cli/server#customized-flags-for-kubernetes-processes)). Persisted configuration normally belongs in `/etc/rancher/k3s/config.yaml` or its drop-ins ([configuration file](https://docs.k3s.io/installation/configuration#configuration-file)). |
| **Every node that may run Substrate workers** | Be Linux; allow Substrate's host paths, capabilities, and unconfined AppArmor/seccomp worker profile; have the proxy ARP/NDP node settings used by Substrate's kind setup; reach the object store, image registries, and pinned gVisor assets. Substrate downloads the architecture-specific `runsc` bundle itself—this is not k3s `RuntimeClass` setup ([k3s node requirements](https://docs.k3s.io/installation/requirements), [gVisor config](https://github.com/agent-substrate/substrate/blob/672533541dbf/manifests/ate-install/sandboxconfig-gvisor.yaml), [worker security context](https://github.com/agent-substrate/substrate/blob/672533541dbf/cmd/atecontroller/internal/controllers/workerpool_apply.go#L327-L400), [node sysctls](https://github.com/agent-substrate/substrate/blob/672533541dbf/hack/create-kind-cluster.sh#L173-L182)). |

## Blockers to clear first

1. **Kubernetes version and certificate APIs.** This pinned Substrate says versions below **1.36 are unsupported**. On 1.36 it requires `certificates.k8s.io/v1beta1` plus `ClusterTrustBundle`, `ClusterTrustBundleProjection`, and `PodCertificateRequest`; its own kind config enables all three gates and the beta API. Its GKE notes say 1.37+ serves the APIs by default, but that is not proof for an arbitrary k3s build ([requirements](https://github.com/agent-substrate/substrate/blob/672533541dbf/tools/setup-gcp/README.md#2-create-cluster), [kind configuration](https://github.com/agent-substrate/substrate/blob/672533541dbf/hack/create-kind-cluster.sh#L103-L113)). As of this research, k3s `stable` is `v1.36.4+k3s1` and `latest` is `v1.37.0+k3s1`; pin an exact k3s release rather than relying on a moving channel ([official channel API](https://update.k3s.io/v1-release/channels), [channel semantics](https://docs.k3s.io/upgrades/manual#release-channels)). Discovery must show both `clustertrustbundles` and `podcertificaterequests` before installation.

2. **A k3s-specific manifest adaptation is required.** Substrate documents development paths for kind and GKE, not k3s ([quickstarts](https://github.com/agent-substrate/substrate/blob/672533541dbf/README.md#quickstart-development)). The generic installer can target an already-authenticated kube context via `KUBECTL_CONTEXT`, but its own renderer calls the non-kind branch “base manifests for GKE” ([installer](https://github.com/agent-substrate/substrate/blob/672533541dbf/hack/install-ate.sh#L319-L342)). Those sources default to GCS, a GKE Managed OTEL endpoint, GCP registry authentication (fatal if its authenticator cannot initialize), and a bundled PostgreSQL `ReadWriteOnce` claim of 500 GiB; the tree also contains a GKE-only `monitoring.googleapis.com/v1` `PodMonitoring` ([telemetry](https://github.com/agent-substrate/substrate/blob/672533541dbf/manifests/ate-install/ate-otel-config.yaml), [atelet manifest](https://github.com/agent-substrate/substrate/blob/672533541dbf/manifests/ate-install/atelet.yaml), [auth behavior](https://github.com/agent-substrate/substrate/blob/672533541dbf/cmd/atelet/main.go#L194-L201), [database claim](https://github.com/agent-substrate/substrate/blob/672533541dbf/manifests/ate-install/postgres/postgres.yaml), [monitoring resource](https://github.com/agent-substrate/substrate/blob/672533541dbf/manifests/ate-install/atenet-router-monitoring.yaml)). The kind wrapper overrides several of these but also hard-codes kind-oriented platform, registry, bucket, and overlay choices ([wrapper](https://github.com/agent-substrate/substrate/blob/672533541dbf/hack/install-ate-kind.sh#L17-L43)). “Bring a context” is source-supported; an upstream-tested k3s bundle is not. Review the fully rendered output and supply a k3s/non-GCP overlay rather than applying either profile unchanged.

3. **Worker capacity is separate from the control plane.** Installing Substrate CRDs/controllers does not by itself give AX somewhere to run. A `WorkerPool` must create ready `ateom-gvisor` workers, and its nodes must carry the install's `ate.dev/substrate-version` label. The counter demo is merely an example three-replica pool, not production sizing ([version labels](https://github.com/agent-substrate/substrate/blob/672533541dbf/README.md#quickstart-development), [example pool](https://github.com/agent-substrate/substrate/blob/672533541dbf/demos/counter/counter.yaml.tmpl)). AX names `ax-system/default-template` as its fallback ActorTemplate but normally builds a task-specific template; determine how template creation and compatible pool capacity will be supplied rather than assuming the control-plane install provides them ([controller configuration](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/deploy/ax-controller.yaml#L71-L83), [template creation](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/substrate/client.go#L278-L303)).

4. **Actor snapshots need their own durable object store.** AX ships a developer-specific GCS default, so `AX_SNAPSHOTS_BUCKET` must be changed ([manifest](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/deploy/ax-controller.yaml#L79-L84)). Substrate's base uses GCS; its kind overlay switches both `atelet` and `ate-api-server` to S3-compatible RustFS. Both components need the same backend and credentials ([base atelet](https://github.com/agent-substrate/substrate/blob/672533541dbf/manifests/ate-install/atelet.yaml), [S3 overlay](https://github.com/agent-substrate/substrate/blob/672533541dbf/manifests/ate-install/kind/kustomization.yaml)). The kind RustFS example is one replica, a 1 GiB `ReadWriteOnce` PVC, and static development credentials, so do not mistake it for a remote-cluster durability design ([RustFS manifest](https://github.com/agent-substrate/substrate/blob/672533541dbf/manifests/ate-install/kind/rustfs.yaml)). Choose and authenticate either GCS or durable S3-compatible storage. k3s `--etcd-s3-*` settings back up **the Kubernetes datastore**, not Substrate actor snapshots ([k3s server storage options](https://docs.k3s.io/cli/server#s3-etcd-snapshot-storage)).

5. **Images must match remote nodes and be pullable there.** The M2 Mac's `arm64` is irrelevant if the k3s workers are `amd64`; conversely, AX's checked-in task-runner build hard-codes `linux/amd64` and is not ready for an arm64-only worker fleet ([Makefile](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/Makefile#L45-L51)). Build every AX/Substrate/task image for the node architecture, publish it to a node-reachable registry, and use digest-pinned task image references; pinned Substrate rejects container images without a digest ([validator](https://github.com/agent-substrate/substrate/blob/672533541dbf/cmd/ateapi/internal/controlapi/actor_template.go#L267-L280)). Do not reuse kind's `localhost:5001`: on remote nodes, localhost means that node. k3s reads private-registry TLS/auth from `/etc/rancher/k3s/registries.yaml` on **each node that pulls**, including schedulable servers, and changes require a k3s restart ([registry documentation](https://docs.k3s.io/installation/private-registry)). That config covers containerd/kubelet pulls; Substrate's `atelet` independently pulls actor images into its cache, so its non-GCP registry authentication must also be designed—the checked-in profiles only wire GCP auth or kind's localhost replacement ([atelet image cache](https://github.com/agent-substrate/substrate/blob/672533541dbf/cmd/atelet/main.go#L194-L215), [kind override](https://github.com/agent-substrate/substrate/blob/672533541dbf/manifests/ate-install/kind/atelet/kustomization.yaml)).

6. **Mac-to-API access and credentials must be deliberate.** k3s's `/etc/rancher/k3s/k3s.yaml` grants unrestricted `system:admin`/`system:masters` access. For an outside client, k3s says to copy it, replace the `server` URL, and refresh the copy after k3s restarts renew its inline certificates; protect it accordingly, or issue narrower credentials instead. The chosen DNS name/IP must be reachable from the Mac and present in the API certificate (`--tls-san`) ([cluster access](https://docs.k3s.io/cluster-access), [listener options](https://docs.k3s.io/cli/server#listeners)).

## Read-only preflight for later

Set `CTX` only when the owner is ready to inspect the cluster; these commands are checks, not evidence that it already qualifies:

```bash
CTX=<remote-k3s-context>
kubectl --context "$CTX" version -o yaml
kubectl --context "$CTX" get --raw /apis/certificates.k8s.io/v1beta1
kubectl --context "$CTX" api-resources --api-group=certificates.k8s.io
kubectl --context "$CTX" get nodes \
  -o custom-columns=NAME:.metadata.name,OS:.status.nodeInfo.operatingSystem,ARCH:.status.nodeInfo.architecture,KUBELET:.status.nodeInfo.kubeletVersion,SUBSTRATE:.metadata.labels.ate\.dev/substrate-version
kubectl --context "$CTX" get storageclass
kubectl --context "$CTX" auth can-i create clusterroles
```

On each intended worker node, later inspect—do not change yet—`sysctl net.ipv4.conf.all.proxy_arp`, IPv6 proxy NDP if applicable, outbound access, available disk, and cluster admission policy for the exact capabilities/host paths/unconfined profiles above. On each k3s server, inspect the effective service arguments and `/etc/rancher/k3s/config.yaml*` for API flags. Missing discovery resources or version `<1.36` is a stop condition.

## Staged no-action plan

1. **Inventory:** record topology (single server or HA), exact k3s/Kubernetes version, every schedulable node's architecture/OS, current server arguments, storage classes, admission policy, registry, and object-store options.
2. **Decide before changing:** select exact compatible revisions, GCS or S3, credentials, remote-node image platforms, registry, WorkerPool size/placement, and a rollback/maintenance window. Render and review the pinned manifests; do not assume current Substrate `main` is compatible with AX's older pin.
3. **Prepare k3s only if preflight fails:** enabling API flags or changing registry configuration restarts k3s. A single-server cluster loses its API during that restart; on HA, keep configuration consistent and change servers one at a time. k3s notes that pods continue during a service restart but does not drain automatically, so plan for API interruption and workload sensitivity ([upgrade behavior](https://docs.k3s.io/upgrades/manual#upgrade-k3s-using-the-installation-script), [single-server versus HA](https://docs.k3s.io/architecture)).
4. **Prove Substrate first:** install the pinned revision through a reviewed non-kind adaptation, then require healthy control-plane pods, certificate resources, `gvisor-default`, version-labelled nodes, a ready gVisor `WorkerPool`, and a successful Substrate actor suspend/resume against the chosen object store. Stop before AX if any layer fails.
5. **Add AX second:** publish node-architecture-correct images, set the real snapshot URI, verify task-specific ActorTemplate creation and compatible worker capacity, deploy AX, and only then use the Mac kube context. AX's automatic port-forward removes the need for a public AX service; it does not remove the need for authenticated network access to the Kubernetes API.

**Bottom line:** remote k3s removes local kind and local Docker from the client-access path, but it is a candidate host—not a drop-in substitute—until all six gates above are proven.
