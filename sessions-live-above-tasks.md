# A multi-task session belongs to the application, not AX

AX currently defines `Task`, `Workspace`, and `Model` resources; it has no `Session` resource or `Task.sessionId` relationship. A `Task` runs one sandboxed command, and binding two Tasks to the same `Workspace` definition prepares **two separate** filesystems—not shared conversation memory ([AX API and Task schema](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/pkg/apis/v1alpha1/ax.proto#L24-L112), [Workspace semantics](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md#L22-L32)).

There are **three different kinds of state**:

1. The *agent's conversation/session*: messages, goal, decisions, summaries, and artifact references. Your agent program or trusted coordinator owns this state; AX has no built-in transcript store.
2. One *AX Task's workspace*: files under its durable `/workspace` survive suspend/resume for **that Task**. AX configures a data-only snapshot; resuming starts a new process, not the old agent's in-memory session. The agent must re-read files if it needs to continue ([AX template snapshot scope](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/substrate/client.go#L238-L275), [runner contract](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L21-L26)).
3. The *shared work product*: a Git commit/branch, patch, or artifact in a coordinator-controlled store. This must be explicitly made available to another Task; it does not travel with an AX `Workspace` resource ([why a team is not an AX manifest](ax-does-not-model-agent-teams.md)).

**A normal agent session is an ordered message history, not a findings summary.** Its harness keeps user and assistant messages plus tool calls and tool results. For each model request it supplies that history (or an explicitly compacted/context-window version); after the response and tool executions it appends the new messages and persists the updated history. While the process remains alive it can keep this in memory. If the Task may be suspended, the harness must also persist its session store under `/workspace` or in an external database, and reopen it on a fresh boot *before* the next model call. AX neither makes these model calls nor records the messages or implements compaction ([Task command](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/sandbox.md#L3-L10), [data-only restart](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L19-L26)).

**What about findings the PR agent did not put in a comment?** Previous user messages, assistant responses, tool calls, and tool outputs remain available *if its harness persisted those turns*; they do not need to appear in the PR comment. For example, after Monday's review the harness can keep its own message log under `/workspace/.agent/` or in a coordinator database; on Thursday a fresh process reloads it and sends the relevant history to the model. Explicit notes about evidence, decisions, and pending questions are optional supplements, not a substitute for the ordinary message history. An observation that never entered a persisted message or note cannot be recovered by AX. Its built-in workspace bootstrap stores its own agent data under `/ax/antigravity`, outside the durable `/workspace` volume ([workspace bootstrap paths](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/workspace/setup.go#L31-L64), [runner volume](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L19-L26)).

**Persistence caution for Git clones:** The default setup marker also lives under `/ax`, and workspace setup uses `git checkout -f` if it runs again. [INFERENCE] Because this AX template only snapshots `/workspace`, relying on an uncommitted tracked Git checkout as the *sole* durable record across a fresh runner boot is risky; setup may replay and overwrite it. No resume was run to determine exactly how the pinned Substrate golden snapshot handles this marker. Preserve important patches/commits in a coordinator-controlled store, and keep the session journal outside the cloned directory or in that store ([setup marker and retry](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/workspace/setup.go#L97-L125), [Git checkout](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/workspace/setup.go#L196-L233), [AX snapshot scope](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/substrate/client.go#L238-L275)).

**Can this be implemented in AX?** Yes *by running an existing agent harness as the Task's `spec.command`*: configure that harness's native session files to live under `/workspace` (outside a Git checkout), or have it use its own external session database. It must reload its complete persisted conversation, append the new user turn delivered by your application, and send the applicable history with each LLM call. AX supplies sandbox, environment setup, and durable files; it has no native chat/session API, memory policy, automatic prompt rehydration, or user-message delivery endpoint. The default runner serves metadata and, only in debug mode, guest services on port 80; a production PR-comment ingress needs an application protocol, such as the agent polling its coordinator, or a custom runner ([Task command and resources](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/pkg/apis/v1alpha1/ax.proto#L24-L112), [runner HTTP contract](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L28-L47), [task networking](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/networking.md#L1-L13)). For **multiple Tasks**, a coordinator must pass versioned session history and code artifacts between isolated sandboxes; naming the same `Workspace` shares a definition, not files. A first-class `Session` resource would be a new AX API/control-plane feature, not a manifest option.

**Is the handoff just copying the harness directory?** For repeated turns of the **same AX Task**, not literally: AX snapshots and restores the Task's entire durable `/workspace` volume on suspend/resume. If both the harness's session files and its edited repository are inside that volume, the snapshot contains both, including uncommitted files; the freshly launched harness still has to reopen its own session. Files elsewhere in the container, such as the default bootstrap's `/ax` directory, are not covered. A **different Task** has its own volume: there is no built-in directory transfer, so the application must export/import the session and work product explicitly ([runner snapshot contract](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L19-L26), [Workspace binding semantics](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md#L22-L32)). The snapshot containing a dirty Git tree does **not** prove it remains intact after the default runner's boot-time setup; see the Git caution above. For important unfinished edits, retain a patch or commit in a coordinator-controlled store before suspend.

**Concrete two-task session:** a trusted coordinator stores `session-42 = {goal: "add JSON output", baseCommit: A, decisions: [...], artifacts: [...]}` outside AX. It launches a `coder` Task at commit A. The coder writes a patch and a short handoff summary, which the coordinator records in `session-42`. After accepting that patch into a new Git revision B, the coordinator launches a **different** `tester` Task from B, giving it the relevant summary and constraints. The tester adds tests and returns another patch. The coordinator associates both Task names and both patches with `session-42`; **AX does not interpret that ID or order their execution**. The coordinator also needs its own success/failure signal, because AX's `Ready` condition is workspace readiness rather than command completion ([runner exit contract](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L30-L43), [brain-to-AX interface](brain-to-ax-interface.md)).

If two activities are merely sequential turns of **one** agent, they can instead run inside a single long-lived Task; its agent program owns the conversation and persists it under `/workspace` if it must survive restart. If two Tasks run **in parallel**, start both from the same versioned session input and let the coordinator reconcile their distinct results; a shared `SESSION_ID` environment value alone shares no data. Keep sensitive history and credentials out of plain `spec.env`: give workers only the context and scoped access each actually needs. No runtime was exercised for this note.
