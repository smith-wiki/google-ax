# A multi-task session belongs to the application, not AX

AX currently defines `Task`, `Workspace`, and `Model` resources; it has no `Session` resource or `Task.sessionId` relationship. A `Task` runs one sandboxed command, and binding two Tasks to the same `Workspace` definition prepares **two separate** filesystems—not shared conversation memory ([AX API and Task schema](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/pkg/apis/v1alpha1/ax.proto#L24-L112), [Workspace semantics](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md#L22-L32)).

There are **three different kinds of state**:

1. The *agent's conversation/session*: messages, goal, decisions, summaries, and artifact references. Your agent program or trusted coordinator owns this state; AX has no built-in transcript store.
2. One *AX Task's workspace*: files under its durable `/workspace` survive suspend/resume for **that Task**. AX configures a data-only snapshot; resuming starts a new process, not the old agent's in-memory session. The agent must re-read files if it needs to continue ([AX template snapshot scope](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/substrate/client.go#L238-L275), [runner contract](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L21-L26)).
3. The *shared work product*: a Git commit/branch, patch, or artifact in a coordinator-controlled store. This must be explicitly made available to another Task; it does not travel with an AX `Workspace` resource ([why a team is not an AX manifest](ax-does-not-model-agent-teams.md)).

**Concrete two-task session:** a trusted coordinator stores `session-42 = {goal: "add JSON output", baseCommit: A, decisions: [...], artifacts: [...]}` outside AX. It launches a `coder` Task at commit A. The coder writes a patch and a short handoff summary, which the coordinator records in `session-42`. After accepting that patch into a new Git revision B, the coordinator launches a **different** `tester` Task from B, giving it the relevant summary and constraints. The tester adds tests and returns another patch. The coordinator associates both Task names and both patches with `session-42`; **AX does not interpret that ID or order their execution**. The coordinator also needs its own success/failure signal, because AX's `Ready` condition is workspace readiness rather than command completion ([runner exit contract](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L30-L43), [brain-to-AX interface](brain-to-ax-interface.md)).

If two activities are merely sequential turns of **one** agent, they can instead run inside a single long-lived Task; its agent program owns the conversation and persists it under `/workspace` if it must survive restart. If two Tasks run **in parallel**, start both from the same versioned session input and let the coordinator reconcile their distinct results; a shared `SESSION_ID` environment value alone shares no data. Keep sensitive history and credentials out of plain `spec.env`: give workers only the context and scoped access each actually needs. No runtime was exercised for this note.
