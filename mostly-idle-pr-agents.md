# A fleet of mostly idle PR agents is a plausible AX use case

**Illustrative workload, not a measured deployment:** a company has 2,000 open pull requests, each with an assistant that can revise code in its own checkout when a reviewer leaves a comment. Perhaps only 20 assistants are doing work at a given moment; most wait for hours or days. Each needs isolation from other repositories and must keep its uncommitted files across interruptions. A Pod kept running for every PR would spend capacity on idle processes; a fresh run-to-completion Job for every comment would require the application to reconstruct the agent's working directory each time ([Substrate's actor/worker rationale](https://github.com/agent-substrate/substrate/blob/22ba860e0f32e20713165b96abd81f6f96da620c/docs/architecture.md#L34-L55), [AX's stated workload motivation](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/README.md#L45-L57)).

1. An **external PR service/coordinator** associates each PR with an AX `Task` and the repository/branch to prepare in a `Workspace`. The agent executable in `spec.command` works in its isolated checkout and persists its own files and a resumable summary under `/workspace`. AX does not write its prompts or conversation history ([Task and Workspace concepts](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md#L5-L32), [sessions live above Tasks](sessions-live-above-tasks.md)).
2. When the PR is idle, the **coordinator explicitly calls** `ax suspend`. AX asks Substrate to snapshot the Task's durable workspace and release worker capacity. **Automatic idle detection is only on AX's roadmap**. In this AX revision, resume restores `/workspace` into a fresh container and process; it does *not* preserve the agent's RAM or make its session state automatic ([AX suspend/resume contract](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#L21-L26), [idle detection roadmap](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/roadmap.md#L15-L23)).
3. A new reviewer comment reaches the external service. It resumes the corresponding Task and delivers the comment through its *own* agent interface. The agent loads its files/summary, edits again, and returns a patch to that service. Agent Substrate assigns active actors to a warm worker pool; **2,000 logical Tasks do not imply 2,000 simultaneously running Pods**, nor do 20 active Tasks imply exactly 20 Pods ([Substrate actor/worker model](https://github.com/agent-substrate/substrate/blob/22ba860e0f32e20713165b96abd81f6f96da620c/docs/glossary.md#L43-L50), [AX task networking](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/networking.md#L1-L13)).

**The advantage being sought** is not smarter planning: it is managing many isolated, checkpointable workspaces over a smaller pool of warm capacity without creating a Kubernetes Pod and reconstructing the checkout on every interaction. AX and Substrate add substantial operational dependencies; this is attractive only if the workload is large and mostly idle enough to justify them. No throughput, cost reduction, or remote-k3s compatibility was verified here ([why AX is not Kubernetes-lite](ax-is-not-kubernetes-lite.md), [who coordinates and receives results](brain-to-ax-interface.md)).
